OrderVault is the escrow account for collateral while an order is live: it receives tokens when the order is funded, holds them through the order's life, and releases them again when the order settles or a cancellation path refunds the user.

This page matches the generated TypeScript client in `packages/contracts/src/clients/order-vault.ts`. The binding is intentionally small: it exposes the two transfer primitives the protocol needs to move collateral into and out of escrow, while the broader order lifecycle is enforced by the router and order handler.

## When to use it {#when-to-use-it}

Use `OrderVault` when you need to answer one of the operational questions users ask most often:

- Where is my collateral while an order is pending?
- What happens to it when the order is executed, cancelled, or expires?
- Which contract is the legal escrow for the order's margin?

For trading flows, [DataStore](/reference/data-store) and [SyntheticsReader](/reference/synthetics-reader) explain the protocol state and market view. `OrderVault` sits one layer closer to custody: it is the on-chain account that receives funded collateral and later returns it.

## Custody lifecycle {#custody-lifecycle}

The practical custody flow is simple and mechanical:

1. The wallet or keeper approves the token and transfers collateral to the `OrderVault` contract.
2. The order is created with the order handler and the vault now carries the escrowed collateral.
3. The order either executes against the protocol or enters a cancellation/expiry path.
4. If the order settles successfully, the vault balance is released as part of the execution flow.
5. If the order is cancelled or fails, the refund path moves the remaining collateral back to the user or the originating account.

The important point is that the vault is not the decision-maker for the order outcome. It records the movement of collateral in and out of custody; the order handler decides whether the order is valid, executable, or cancelled.

The interface therefore treats `OrderVault` as a custody ledger, not as the source of market or risk logic. That matches the generated client: it has no read-only state introspection, no order-level settlement logic, and no custom domain enum for every lifecycle outcome.

## API coverage {#api-coverage}

The generated binding exposes the following public methods. This list is asserted against `OrderVaultClient` and the transfer primitives it wraps.

| Function | Parameters | Returns | Errors |
| --- | --- | --- | --- |
| `transferOut` | `account: string`, `token: string`, `amount: bigint` | `xdr.ScVal` | RPC or simulation error if the vault cannot release funds or the call is not authorized |
| `recordTransferIn` | `account: string`, `token: string`, `amount: bigint` | `xdr.ScVal` | RPC or simulation error if the vault cannot record an incoming balance |

The TypeScript binding does not define a typed error enum for these calls. In normal Soroban usage, failures surface as RPC or simulation exceptions instead of a domain-specific `Result` enum on the client.

### Parameter semantics

- `account` is the user or counterparty address that owns the collateral movement.
- `token` is the Stellar token contract ID for the collateral asset being moved.
- `amount` is a raw Soroban integer in the token's smallest unit. For a 7-decimal token, `2500000000000000n` means `2.5` tokens.

This matches the rest of the protocol: amounts are not formatted in the contract call, and the UI converts to user units after the read/simulation returns.

## Auth and cancellation behavior {#auth-and-cancellation-behavior}

The generated client does not expose a separate `cancel_order` or `refund` method. That is a signal that the vault is deliberately narrow: it does not make the order decision itself. Instead, the protocol's order and execution flows decide whether an order is live, expired, failed, or cancelled, and then call the vault to move funds.

In practice, this means the refund path is governed by the order lifecycle rather than by a separate vault authorization gate:

- a successful execution consumes the pre-funded collateral from the vault as part of order settlement;
- a failed or expired order should leave the vault in a recoverable state such that the original user can receive the unused collateral back;
- a cancellation path releases the escrowed amount through the vault transfer-out primitive.

The key security rule is simple: the OrderVault escrow is only as safe as the order handler's settlement logic. If the order never reaches a valid executed state, the refund path must release the deposit to the correct account and not leave a stranded balance in custody.

## Worked example: cancelled order {#worked-example}

Consider a trader who opens a market increase with `2.5` TUSDC as collateral.

```ts
const account = "GD...TRADER"
const token = "CBAN5YU3KRDKPTQ2H76D6S7HQFPRBGUD524F65BUM2RQCITPTRLKWKES"
const amount = 2_500_000_000_000_000n // 2.5 TUSDC at 7 decimals

await orderVault.recordTransferIn(account, token, amount)
// order is created and remains in the order vault while live

// later, the order is cancelled or expires
await orderVault.transferOut(account, token, amount)
```

This is the mental model for a cancelled order:

1. `recordTransferIn` marks the collateral as escrowed in the vault.
2. The order remains live until the order handler decides it is invalid, expired, or cancelled.
3. The refund path calls `transferOut` back to the original account.
4. The remaining collateral is no longer trapped behind the live order.

For an order that fails at execution or expires before it can be filled, the same pattern applies: the contract should not leave a stale escrowed balance without a valid settlement path. In other words, the vault keeps the funds safe until the protocol decides the order is finished.

## Implementation notes {#implementation-notes}

The generated client is intentionally minimal. It records only the two transfer primitives the OrderVault contract needs to support escrow movement:

- `recordTransferIn` to accept collateral into custody
- `transferOut` to release collateral when the order settles or is cancelled

This is why the vault is best thought of as the escrow ledger for live orders rather than as a full order-management API. The actual lifecycle rules live in the order and execution handlers, while the vault only enforces the asset movement that those lifecycle decisions require.
