SO4 has one design system, defined entirely in [`packages/ui/src/styles/globals.css`](https://github.com/SO4-Markets/interface/blob/main/packages/ui/src/styles/globals.css) and enforced by `bun run check:tokens`. This page explains the roles and the contract; it does not restate them — see [Design tokens](/reference/tokens.generated) for the generated, always-current list of every token, its light and dark value, and the Tailwind utility it powers, and [`DESIGN.md`](https://github.com/SO4-Markets/interface/blob/main/DESIGN.md) for the full written rationale behind each decision below.

## Why there is no tailwind.config.js

Tailwind v4 moved configuration into CSS itself. There is no JS config file to check for drift against the CSS, no two places a token can disagree, and no build step that has to keep a JS object and a stylesheet in sync — the `@theme` block in `globals.css` *is* the configuration. For a contributor this means:

- Adding a color, radius, or spacing step is one edit, in one file, in CSS.
- `bg-surface-raised` works because `--color-surface-raised` exists in `@theme inline` — there is no separate `theme.extend.colors` entry to remember.
- A raw hex color or an arbitrary value (`text-[13px]`) can't hide behind "it's in the config somewhere" — `check:tokens` (below) catches it because there's exactly one source of truth to check against.
- If you're used to `tailwind.config.js`, the CSS-first mental model is: everything that used to be `theme.extend.X` is now a `--X-name: value` declaration inside `@theme`.

## Surface roles

Five explicit layers replace the generic shadcn page/card/popover pattern, so which surface a piece of UI sits on is always a deliberate choice rather than an accident of which component happened to be reached for:

| Use | Token |
|---|---|
| Base page background | `bg-surface-canvas` |
| Inset/recessed areas — well containers, stat cards | `bg-surface-sunken` |
| Elevated above canvas — cards, panels | `bg-surface-raised` |
| Floating on top of everything — modals, popovers | `bg-surface-overlay` |
| Hoverable/active areas — buttons, table rows | `bg-surface-interactive` |

Pick by what the element *is doing*, not by how it currently looks: a card that becomes clickable moves from `surface-raised` to `surface-interactive` on hover/active state, it doesn't get a one-off darker shade invented for it.

## Text and icon roles

Six roles replace scattered opacity modifiers (`text-foreground/70`, `text-foreground/50`, ...) with named intent:

| Use | Token |
|---|---|
| Default body text, headings | `text-text-primary` |
| Supporting labels, descriptions | `text-text-secondary` |
| Placeholders, hints, metadata | `text-text-tertiary` |
| Inactive UI elements | `text-text-disabled` |
| Text on solid color fills (badges, buttons) | `text-text-inverse` |
| Interactive/navigation text | `text-text-link` |

An opacity modifier on `text-foreground` and one of these roles can look identical at a single breakpoint in a single theme and then diverge the moment either changes — the role is the one that's guaranteed to stay legible.

## One theme, so far {#one-theme-so-far}

`surface-*` and `text-*` (`primary`, `secondary`, `tertiary`, `disabled`, `inverse`, `link`) are defined in both `:root` and `.dark`, so the utilities resolve in either theme. In light mode the status colours (`success`, `warning`, `liquidation`) are darkened to clear 4.5:1 on white, and the `*-subtle` / `*-border` tints are light fills; `.dark` restores the brighter values and the dark-tuned tints. The `--chart-*` tokens follow the same split, and the sRGB fallbacks in `chart-theme.ts` mirror them. Use the surface/text roles rather than the older `--background`/`--foreground`/`--card`/`--popover` aliases in new code.

## Trading-state and semantic colors

Long, short, and liquidation states, plus semantic status (success, warning, info, danger, neutral), each carry three tokens — foreground, subtle background, and border — so a filled badge and its outlined counterpart always agree:

```
bg-long-subtle border-long-border      /* long position badge, outlined */
bg-short-subtle border-short-border    /* short position badge, outlined */
bg-liquidation-subtle border-liquidation-border
```

Color is never the only signal on a trading state — pair it with a label, icon, or position (a "Long"/"Short" badge text, an up/down glyph), because color alone fails for colorblind users and in bright sunlight on a phone screen. Chart series colors (`chart-1`–`chart-5`) map onto this same palette (long, short, liquidation, info, neutral) rather than introducing a separate chart-only set, so a green candle and a positive PnL number are the same green.

## When to reach for something else

- **Radius** — use `rounded-sm`/`md`/`lg`/`xl`/`full`, not an arbitrary value and not the bare `rounded` class (the check rejects both). `sm` is buttons/inputs/badges/tabs, `md` dropdowns and tooltips, `lg` cards and toasts, `xl` modals.
- **Elevation** — use `shadow-xs`/`sm`/`md`/`lg`/`xl`: `xs` resting controls, `sm` raised controls, `md` tooltips and dropdowns, `lg` toasts and sheets, `xl` modals. Don't use bare `shadow` or `shadow-[...]`.
- **Type size** — the default Tailwind scale (`text-xs`…`text-2xl`) skips too many steps for this app's dense tables (order books, position rows). Check the named micro-typography scale in [Design tokens](/reference/tokens.generated#micro-typography-scale) before reaching for `text-[13px]`.
- **Monospace** — `font-mono` (Geist Mono) is for order book prices/sizes, addresses and transaction hashes, and code — not the default body font.

## The check:tokens contract

[`scripts/check-design-tokens.ts`](https://github.com/SO4-Markets/interface/blob/main/scripts/check-design-tokens.ts), run as `bun run check:tokens` and wired into CI, scans `apps/web/src` and `packages/ui/src` for raw hex colors, arbitrary font-size classes (`text-[...]`), and arbitrary radius classes (`rounded-[...]`), the bare `rounded` class. It is part of the [commit gate](https://github.com/SO4-Markets/interface/blob/main/AGENTS.md) — nothing merges without it passing, and a `ds-allow` comment or allowlist entry is only for values that are structurally unable to be a token (a third-party library's imperative color config, an HTML `<meta>` tag), each with a reason attached, never a way to route around adding a token that should exist. See every current exception and the full audit history in [`DESIGN.md`](https://github.com/SO4-Markets/interface/blob/main/DESIGN.md#audit-history).

## See it live

Every `packages/ui` primitive, across every variant and both themes, renders on the component gallery at `/gallery` in a local `apps/web` dev server (`bun run --cwd apps/web dev`, then visit `http://localhost:3000/gallery`) — it isn't linked from the app's navigation because it's a development tool, not a trader-facing page. It's also the fixed target for the visual regression suite (`e2e/design-system-visual.spec.ts`) and includes an RTL toggle for checking directional CSS. Use it to see a token in a real component before you use it in a new one.
